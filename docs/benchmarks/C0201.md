# C0201 camera reference benchmark

Measured on 2026-10-24 using `tests/clips/C0201.MP4`. This is real camera
footage with handheld movement, moving divers/fish/sharks, and visible seabed.
The media and generated exports stay local; generated files are under
`benchmarks/results/C0201/` and excluded from version control.

## Input and method

- AMD Ryzen 7 5800X (8 cores / 16 threads), Python 3.14.4, NumPy 2.3.5,
  FFmpeg 8.0.1-3ubuntu2. Optional C extension compiled locally with GCC.
- 1920×1080 H.264/XAVC, 8-bit YUV 4:2:0, 100 fps, 24.48 seconds,
  2,448 frames, one PCM audio stream.
- Metadata reports BT.709 primaries and `iec61966-2-4` transfer. The application
  treats the camera picture profile as ambiguous. **Rec.709 was selected
  provisionally for timing; color accuracy has not been established.**
- Classical automatic analysis; default manual controls; SDR H.264 output at
  CRF 17, preset `fast`, at most eight encoder threads.
- First approximately two seconds were stream-copied into `sample.mov` without
  changing video pixels. The trim contains 201 frames and one final 20 ms frame
  interval, so it exercises variable-frame-rate preservation. The original
  full clip has constant 10 ms intervals.
- Analysis ran once and was reused across the five sequential sample exports.
  Analysis took 1.96 seconds, excluded from the export timings below. Export
  timings include timestamp scanning, decoding, finishing/color processing,
  encoding, audio muxing, and output validation.
- Each scenario ran once. These are observed wall-clock results, not controlled
  repeated-trial statistics. A source timestamp inspection overlapped part of
  the C-only sample run; small differences among C scenarios are not conclusive.

## Sample export results

| Scenario | Elapsed | Export fps | Relative to source playback | Output size |
| --- | ---: | ---: | ---: | ---: |
| NumPy, color only | 59.81 s | 3.36 | 0.034× | 5,127,581 bytes |
| C, color only | 43.00 s | 4.67 | 0.047× | 5,127,581 bytes |
| C, stabilized | 44.37 s | 4.53 | 0.045× | 5,054,586 bytes |
| C, denoise strength 3 | 43.18 s | 4.65 | 0.047× | 3,342,215 bytes |
| C, stabilized + denoise 3 | 42.97 s | 4.68 | 0.047× | 3,338,870 bytes |

The C-only export takes 28.1% less time (1.39× throughput) than NumPy. Both
color-only exports have the **same SHA-256**, providing a byte-for-byte output
comparison for this sample:

`f48ce71b11fab47a4ee8eecdc34c003299de27b9809159f1faceae1f4db4e3ee`

A separate first-200-frame decode/finishing diagnostic, without grading or
encoding, measured 81.0 fps with effects off, 25.5 fps with stabilization,
78.9 fps with denoise, and 21.5 fps with both. Thus stabilization itself is
costly, but the slower color-processing stage largely hides this extra cost
in complete exports. The earlier 4× LUT microbenchmark does not describe this
classical matrix-based camera export. End-to-end rendering remains far below
100 fps real time.

## Complete clip export

The full **24.48-second / 2,448-frame** clip was exported with the C backend,
stabilization enabled, and denoise strength 3:

- Automatic analysis: **23.22 seconds**, excluded from export time.
- Complete export: **533.17 seconds (8 min 53 s)**.
- Throughput: **4.59 fps**, or **0.046× real time**.
- Output: 89,777,573 bytes; 1920×1080, 2,448 frames, 24.48 seconds,
  constant 100 fps, one audio stream. Frame count, duration, audio-stream count,
  and requested color signaling passed the render validation.
- Local review file:
  `benchmarks/results/C0201/full-provisional-rec709-stabilized-denoised.mp4`.
  Rec.709 interpretation is provisional; this is not a verified reference grade.

Source analysis identified one continuous shot and warned that the red channel
has little usable signal. Rendering spent approximately 22 seconds validating
source timestamps before the first frame. This scan, plus output validation,
adds decoding work outside the per-frame color pipeline.

The full run confirms that the current CPU pipeline remains slow on this
100 fps source: roughly 21.8 seconds of export time per second of footage.
C acceleration helps, but this benchmark does not establish real-time export
performance or successful stabilization.

## Stabilization diagnostic

OpenCV 4.10 tracks features in the lower-right seabed rectangle
`(left=.60, top=.65, right=.95, bottom=.95)` on 640-pixel, 25 fps proxies.
Forward/backward optical flow checks and RANSAC reject inconsistent tracks.
Differences between successive displacement estimates suppress a steady pan;
the resulting acceleration RMS is a **diagnostic**, not a ground-truth quality
score. Foreground occlusion, parallax, rotation, and weak seabed texture can
still bias it.

The unmodified export yielded 39/49 valid frame pairs; stabilized yielded
41/49. Comparing only the same 30 adjacent valid estimates:

| Variant | Background translation acceleration RMS, proxy pixels |
| --- | ---: |
| Color only | 1.749 |
| Stabilized | 2.033 |

This metric worsens by approximately 16.2% on the short sample. The current
whole-frame FFmpeg stabilizer does **not demonstrate an improvement** against
the seabed reference. It does not explicitly select the sand as its tracking
reference. Robust background selection and further full-clip visual assessment
are needed before claiming stabilization quality on this material.

## Reproduction

Use the actual camera recording profile in place of the provisional `rec709`
when it is known. Use fresh output directories to preserve previous exports.

```bash
ffmpeg -i tests/clips/C0201.MP4 -t 2 -map 0:v:0 -map '0:a?' -c copy /tmp/C0201-sample.mov
python3 -m benchmarks.export --clip /tmp/C0201-sample.mov --input-profile rec709 \
  --finishing --output-dir /tmp/C0201-exports --report /tmp/C0201-report.json
python3 -m benchmarks.stabilization /tmp/C0201-exports/native.mp4 \
  /tmp/C0201-exports/native-stabilized.mp4 --report /tmp/C0201-motion.json
```

The stabilization diagnostic needs optional OpenCV Python bindings (`cv2`).
OpenCV is not required to launch the application or run its existing FFmpeg
stabilizer.

To repeat only the complete C export with the saved full-clip settings:

```bash
python3 -m benchmarks.export \
  --project benchmarks/results/C0201/full-provisional-rec709.uwcc-project.json \
  --backend native --output-dir /tmp/C0201-full-repeat \
  --report /tmp/C0201-full-repeat.json
```
